bunqueue supports two deployment modes: **Embedded** (direct SQLite) and **TCP** (network + SQLite). This page shows real benchmark results comparing both modes at scale.

<Aside type="tip">
The only honest benchmark is one you run on your own hardware. Clone the repo and run `bun run bench/comprehensive.ts` to verify these results. Every figure below is the **median of 3 runs** of that exact script on an Apple M1 Max (Bun 1.3.14); single runs vary ±10–20%, so re-run a few times.
</Aside>

## Install Footprint

Throughput isn't the only number that shrank. A clean `bun add bunqueue` is a featherweight install — re-measured on 2.8.24:

| Metric | bunqueue 2.8.24 | Before (2.7.x) | Change |
|--------|----------------|----------------|--------|
| `node_modules` size | 5.5 MB | 93 MB | **−94%** |
| packages installed | 7 | 117 | **117 → 7** |
| cold install time | ~1.7 s | ~6 s | **~3.5× faster** |

bunqueue ships just **2 runtime dependencies** — `croner` (cron parsing) and `msgpackr` (binary serialization). SQLite, S3, HTTP, and WebSocket are all built into Bun, so there's nothing else to download. The MCP server's `@modelcontextprotocol/sdk` is an **optional peer dependency**: queue and worker users never pull it in, and you install it once only if you run `bunqueue-mcp`.

<Aside>
The 2.8.0/2.8.1 MCP refactor removed the SDK, `zod`, and the HTTP stack from the install path; 2.8.2 dropped 2.8 MB of unusable sourcemaps from the published package. A new user goes from ~6s to ~1.2s on a cold install.
</Aside>

|-------|------|-----------|---------|
| **1,000** | 33,209 ops/sec | 34,470 ops/sec | 173 ops/sec |

<Aside>
¹ The TCP **Push** column issues jobs in **batches of 100 concurrent `add()` calls** (auto-batched into `PUSHB` frames on the wire), not one awaited add at a time — a single *sequential* awaited `add()` over TCP is ~10K ops/sec (one round-trip per job). It scales to **90K ops/sec** at 50K jobs; bulk push (`addBulk`) peaks around **76K ops/sec**, both amortized with connection pooling (32 connections).
</Aside>

<Aside type="caution">
**Read the Process column carefully.** It measures a *single* worker process at `concurrency: 10` draining the queue over the network. Each job's lock lease is bounded by the worker's free concurrency slots (the over‑pull guard), so in steady state the worker issues roughly one pull round‑trip per freed slot — the per‑job network latency, not server throughput, is the bottleneck. Throughput therefore scales with worker concurrency and the number of worker processes, **not** with queue depth (median of 3, 5K jobs):

| Worker concurrency | TCP process (ops/sec) |
|--------------------|-----------------------|
| 10 (default in the bench) | ~182 |
| 50 | ~4,900 |
| 100 | ~4,500 |

Real distributed deployments run many workers and/or higher concurrency, so per‑node processing throughput is in the thousands of ops/sec; for maximum single‑process throughput use **embedded mode** (no network round‑trip per pull). Earlier versions of this page reported much higher single‑worker TCP process numbers that predate the lease‑bounding correctness fix and no longer reproduce.
</Aside>

## Benchmark Methodology

The benchmark tests three operations at four different scales (1K, 5K, 10K, 50K jobs):

### 1. Push Test

The two modes push **differently**, so the "Push" column is not the same operation across modes:

- **Embedded** awaits each `add()` one at a time (true sequential single-job insertion):

```typescript
for (let i = 0; i < scale; i++) {
  await queue.add('job', PAYLOAD); // embedded
}
```

- **TCP** issues jobs in batches of 100 concurrent `add()` calls (which the client auto-batches into `PUSHB` frames), to exercise pipelining — a single awaited `add()` over TCP is round-trip-bound at ~10K ops/sec:

```typescript
for (let i = 0; i < scale; i += 100) {       // TCP
  await Promise.all(
    Array.from({ length: 100 }, () => queue.add('job', PAYLOAD))
  );
}
```

### 2. Bulk Push Test
Push jobs in batches of 100 to measure bulk insertion efficiency.

```typescript
const jobs = Array.from({ length: 100 }, (_, i) => ({
  name: 'bulk-job',
  data: { ...PAYLOAD, i },
}));

for (let i = 0; i < scale / 100; i++) {
  await queue.addBulk(jobs);
}
```

### 3. Process Test
Push jobs in parallel batches of 500, then drain them with a **single worker at `concurrency: 10`** (one process, ten in-flight jobs — not ten worker processes). Over TCP this is bound by per-pull round-trip latency (see the caution box above); embedded has no such bound.

```typescript
// Push in parallel batches
for (let i = 0; i < scale; i += 500) {
  const promises = [];
  for (let j = 0; j < Math.min(500, scale - i); j++) {
    promises.push(queue.add('job', PAYLOAD));
  }
  await Promise.all(promises);
}

// Wait for all to complete
while (processed < scale) {
  await sleep(5);
}
```

## Why bunqueue is Fast

<CardGrid>
  <Card title="SQLite WAL Mode" icon="seti:db">
    Concurrent reads/writes with memory-mapped I/O via Bun's native FFI bindings.
  </Card>
  <Card title="Auto Sharding" icon="puzzle">
    Auto-detected from CPU cores (power of 2, max 64). Minimizes lock contention.
  </Card>
  <Card title="TCP Pipelining" icon="rocket">
    Multiple commands in flight per connection with reqId-based response matching.
  </Card>
  <Card title="Efficient Structures" icon="seti:config">
    4-ary MinHeap for O(log4 n) priority queues. Skip lists for temporal indexing. LRU caches.
  </Card>
</CardGrid>

## Dependency Chain Latency

Jobs with dependencies (`dependsOn`, `FlowProducer`, parent-child workflows) benefit from event-driven dependency resolution via microtask coalescing, replacing the previous 100ms polling interval.

### Before (polling 100ms via setInterval)

| Scenario | Avg | P50 | P95 | P99 |
|----------|-----|-----|-----|-----|
| **Single dep (A&rarr;B)** | 100.09ms | 100.05ms | 101.91ms | 103.90ms |
| **Chain dep (4 levels)** | 300.83ms | 300.43ms | 304.19ms | 306.72ms |
| **Fan-out (1&rarr;5)** | 100.21ms | 100.11ms | 101.88ms | 105.37ms |

### After (event-driven via microtask)

| Scenario | Avg | P50 | P95 | P99 |
|----------|-----|-----|-----|-----|
| **Single dep (A&rarr;B)** | 26.4&micro;s | 14.4&micro;s | 61.7&micro;s | 114.2&micro;s |
| **Chain dep (4 levels)** | 32.5&micro;s | 30.7&micro;s | 47.0&micro;s | 67.5&micro;s |
| **Fan-out (1&rarr;5)** | 36.6&micro;s | 27.7&micro;s | 48.1&micro;s | 141.2&micro;s |

### Improvement

| Scenario | Before P50 | After P50 | Speedup |
|----------|-----------|----------|---------|
| **Single dep (A&rarr;B)** | 100.05ms | 0.014ms | **~6,900x** |
| **Chain (4 levels)** | 300.43ms | 0.031ms | **~9,800x** |
| **Fan-out (1&rarr;5)** | 100.11ms | 0.028ms | **~3,600x** |

<Aside type="tip">
Dependency chain latency dropped from **hundreds of milliseconds** to **microseconds**. This means multi-step pipelines (ETL, workflows, map-reduce) resolve nearly instantly instead of waiting for polling intervals.
</Aside>
