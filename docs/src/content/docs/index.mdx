  <span class="bq-eyebrow">vs bullmq</span>
  <h2 class="bq-h2">Same job, three fewer boxes.</h2>
  <p class="bq-lede">BullMQ is excellent software that requires Redis. bunqueue removes the requirement: the queue lives in your process and persists to one file. Coming from Celery, Sidekiq or asynq instead? Same trade: the broker box is the part that disappears.</p>

<div class="bq-wrap bq-section">
  <span class="bq-eyebrow">trade-offs</span>
  <h2 class="bq-h2">Where bunqueue stops.</h2>
  <p class="bq-lede">Single-instance by design: one process owns the SQLite file. That is exactly what deletes the Redis box, and it draws a clear line. Read this before you adopt.</p>

  <div class="bq-trust">
    <div class="bq-trust-card">
      <span class="bq-tag">availability</span>
      <h3>No clustering, no failover</h3>
      <p>One server process owns the queue. Disaster recovery is S3 backup plus restore on a new host, not automatic failover. If the queue itself must span servers, BullMQ on Redis Cluster is the better fit, <a href="/guide/comparison/">we say so in the comparison</a>.</p>
    </div>
    <div class="bq-trust-card">
      <span class="bq-tag">durability</span>
      <h3>Buffered writes by default</h3>
      <p>Writes are batched for up to 10ms, that buffer is what buys ~100K jobs/sec. A hard crash inside the window can lose those jobs. Jobs that cannot tolerate it take <code>{"{ durable: true }"}</code> and hit disk before <code>add()</code> returns.</p>
    </div>
    <div class="bq-trust-card">
      <span class="bq-tag">scaling</span>
      <h3>Workers scale, the server does not</h3>
      <p>Any number of worker processes on any machines connect over TCP, that is the scaling path. For edge and multi-site setups, run local embedded queues and drain them to a central server with <a href="/guide/iot-edge/">forward()</a>.</p>
    </div>

<div class="bq-wrap bq-section">
  <span class="bq-eyebrow">sqlite, seriously?</span>
  <h2 class="bq-h2">The questions everyone asks.</h2>

  <div class="bq-trust">
    <div class="bq-trust-card">
      <h3>Can SQLite handle a production queue?</h3>
      <p>In WAL mode, yes: reads and writes overlap and the write path is one batched transaction. Measured at 630K jobs/sec bulk push embedded and 90K over TCP, <a href="/guide/benchmarks/">numbers and methodology here</a>.</p>
    </div>
    <div class="bq-trust-card">
      <h3>What happens on a crash?</h3>
      <p>Jobs live in SQLite, so a restart recovers waiting, delayed and active jobs. A worker that dies mid-job is caught by stall detection and its jobs are requeued. Jobs that keep failing land in the dead letter queue, kept and retryable.</p>
    </div>
    <div class="bq-trust-card">
      <h3>Locks? "database is locked"?</h3>
      <p>Not in the supported topology: exactly one process opens the file, embedded in your app or as the server, and any number of workers connect over TCP. Two processes on one file is the single thing the docs tell you not to do.</p>
    </div>
