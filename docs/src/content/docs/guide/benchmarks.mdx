  <Aside>
  The TCP **Push** chart issues jobs in **batches of 100 concurrent `add()` calls** (auto-batched into `PUSHB` frames on the wire), not one awaited add at a time, a single *sequential* awaited `add()` over TCP is ~10K ops/sec (one round-trip per job).
  </Aside>

  <Aside type="caution">
  **Read TCP processing numbers carefully.** The bench drains the queue with a *single* worker at `concurrency: 10`: each job's lock lease is bounded by the worker's free concurrency slots (the over-pull guard), so per-job network latency, not server throughput, is the bottleneck, and a single c=10 worker measures ~180 ops/sec. Throughput scales with worker concurrency and worker count, **not** queue depth (median of 3, 5K jobs):

  | Worker concurrency | TCP process (ops/sec) |
  |--------------------|-----------------------|
  | 10 (bench default) | ~182 |
  | 50 | ~4,900 |
  | 100 | ~4,500 |

  Real deployments run many workers and/or higher concurrency, so per-node processing sits in the thousands of ops/sec; for maximum single-process throughput use **embedded mode**. Earlier versions of this page reported much higher single-worker TCP process numbers that predate the lease-bounding correctness fix and no longer reproduce.
  </Aside>

  <p class="bq-lede">Throughput isn't the only number that shrank. bunqueue ships <b>2 runtime dependencies</b>, <code>croner</code> and <code>msgpackr</code>. SQLite, S3, HTTP and WebSocket are built into Bun.</p>

  | Metric | bunqueue 2.8.30 | Before (2.7.x) | Change |
  |--------|----------------|----------------|--------|
  | `node_modules` size | 5.5 MB | 93 MB | **−94%** |
  | packages installed | 7 | 117 | **117 → 7** |
  | cold install time | ~1.7 s | ~6 s | **~3.5× faster** |

  <Aside>
  The 2.8.0/2.8.1 MCP refactor removed the SDK, `zod`, and the HTTP stack from the install path; 2.8.2 dropped 2.8 MB of unusable sourcemaps from the published package. The MCP server's `@modelcontextprotocol/sdk` is an **optional peer dependency**: queue and worker users never pull it in.
  </Aside>

<div class="bq-wrap bq-section">
  <span class="bq-eyebrow">methodology</span>
  <h2 class="bq-h2">How the numbers are made.</h2>
  <p class="bq-lede">Three operations at four scales, 1K, 5K, 10K, 50K jobs, each cell the median of 3 runs. The two modes push differently, and we say so.</p>

  **Push.** Embedded awaits each `add()` one at a time (true sequential insertion). TCP issues jobs in batches of 100 concurrent `add()` calls, which the client auto-batches into `PUSHB` frames, a single awaited `add()` over TCP is round-trip-bound at ~10K ops/sec:

```typescript
for (let i = 0; i < scale; i++) {
  await queue.add('job', PAYLOAD); // embedded: sequential
}

for (let i = 0; i < scale; i += 100) { // TCP: 100 concurrent
  await Promise.all(
    Array.from({ length: 100 }, () => queue.add('job', PAYLOAD))
  );
}
```

  **Bulk push.** Batches of 100 through `addBulk`:

```typescript
const jobs = Array.from({ length: 100 }, (_, i) => ({
  name: 'bulk-job',
  data: { ...PAYLOAD, i },
}));

for (let i = 0; i < scale / 100; i++) {
  await queue.addBulk(jobs);
}
```

  **Process.** Push in parallel batches of 500, then drain with a **single worker at `concurrency: 10`**, one process, ten in-flight jobs. Over TCP this is bound by per-pull round-trip latency (see the caution above); embedded has no such bound.

```typescript
for (let i = 0; i < scale; i += 500) {
  const promises = [];
  for (let j = 0; j < Math.min(500, scale - i); j++) {
    promises.push(queue.add('job', PAYLOAD));
  }
  await Promise.all(promises);
}

while (processed < scale) {
  await sleep(5);
}
```

  ### Environment

  Apple M1 Max (10 cores) · 32 GB RAM · SSD · macOS 26.5 · Bun 1.3.14 · 16 shards auto-detected · payload 111 bytes · 32-connection pool (TCP) · every cell the **median of 3 runs**. Single runs vary ±10 to 20% with warmup and background load; the 1K rows in particular reflect cold start.

<div class="bq-wrap bq-section">
  <span class="bq-eyebrow">reproduce</span>
  <h2 class="bq-h2">Run it on your hardware.</h2>
  <p class="bq-lede">The only honest benchmark is one you run yourself. The full script is <a href="https://github.com/egeominotti/bunqueue/blob/main/bench/comprehensive.ts"><code>bench/comprehensive.ts</code></a>.</p>

```bash
git clone https://github.com/egeominotti/bunqueue.git
cd bunqueue && bun install

bun run start &                  # server, for the TCP half
bun run bench/comprehensive.ts   # the numbers on this page

redis-server --daemonize yes     # optional: BullMQ comparison
bun run bench/comparison/run.ts
```

  <Aside>
  Run the benchmark **without** `BUNQUEUE_EMBEDDED=1` in the environment. That variable forces every queue/worker into embedded mode (it is used by the test preload), which would make the TCP half silently run in-process and report embedded numbers under a TCP label.
  </Aside>

  Other benchmarks in the repo: [`src/benchmark/throughput.bench.ts`](https://github.com/egeominotti/bunqueue/blob/main/src/benchmark/throughput.bench.ts) (individual operations), [`src/benchmark/worker.bench.ts`](https://github.com/egeominotti/bunqueue/blob/main/src/benchmark/worker.bench.ts) (realistic worker simulation), [`src/benchmark/stress.bench.ts`](https://github.com/egeominotti/bunqueue/blob/main/src/benchmark/stress.bench.ts) (production validation), [`src/benchmark/million-jobs.bench.ts`](https://github.com/egeominotti/bunqueue/blob/main/src/benchmark/million-jobs.bench.ts) (high-volume integrity).

<div class="bq-wrap bq-section">
  <span class="bq-eyebrow">why it's fast</span>
  <h2 class="bq-h2">No magic, four decisions.</h2>
  <div class="bq-tools">
    <div class="bq-tool">
      <BqIcon name="file" />
      <h3>SQLite WAL mode</h3>
      <p>Concurrent reads and writes with memory-mapped I/O through Bun's native SQLite bindings, no serialization layer between the queue and its store.</p>
    </div>
    <div class="bq-tool">
      <BqIcon name="shards" />
      <h3>Auto sharding</h3>
      <p>Shard count auto-detected from CPU cores (power of 2, max 64). Queues hash to shards, so hot queues don't contend on one lock.</p>
    </div>
    <div class="bq-tool">
      <BqIcon name="network" />
      <h3>TCP pipelining</h3>
      <p>Multiple commands in flight per connection with request-ID response matching, msgpack framing, and transparent client-side batching into <code>PUSHB</code>.</p>
    </div>
    <div class="bq-tool">
      <BqIcon name="stack" />
      <h3>Efficient structures</h3>
      <p>4-ary min-heap for O(log₄ n) priority queues, skip lists for temporal indexing, LRU caches with hard memory bounds.</p>
    </div>
  </div>
