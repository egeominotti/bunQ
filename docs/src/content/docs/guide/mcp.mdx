## Quick Start

<Steps>
1. **Install bunqueue**, the MCP server (`bunqueue-mcp`) ships as a binary *inside* the `bunqueue` package. There is no standalone `bunqueue-mcp` package on npm, so `bunqueue` must be installed first.

   ```bash
   bun add bunqueue          # in your project, for Claude Code
   # or, for Claude Desktop / Cursor / Windsurf (they start the server outside your project):
   bun add -g bunqueue       # global install, puts bunqueue-mcp on your PATH
   ```

2. **Install the MCP SDK**, since v2.8.1, `@modelcontextprotocol/sdk` is an **optional peer dependency**: it's only needed to run the MCP server, so queue-only users don't download it. Install it once in the same project/environment where the server runs:

   ```bash
   bun add @modelcontextprotocol/sdk
   ```

3. **Connect your AI client**

   ```bash
   claude mcp add bunqueue -- bunx bunqueue-mcp
   ```

4. **Start using it**

   Ask your agent: *"Add a job to the emails queue"*, it works immediately. The MCP server starts as a child process, communicates via stdio, and the agent can call any of the 73 tools.
</Steps>

<Aside type="caution" title="bunx bunqueue-mcp returns a 404?">
  `bunqueue-mcp` is **not** a standalone npm package, it's a binary bundled with `bunqueue`. Running `bunx bunqueue-mcp` before installing `bunqueue` makes `bunx` try to download a package named `bunqueue-mcp`, which doesn't exist (`error: GET https://registry.npmjs.org/bunqueue-mcp - 404`). Install `bunqueue` first (`bun add bunqueue`, or `bun add -g bunqueue` for global use) so `bunx` resolves the bundled binary. As a no-install one-liner, `bunx --package=bunqueue bunqueue-mcp` always fetches the latest published `bunqueue` and runs its MCP binary.
</Aside>

<Aside type="caution" title="The MCP server needs @modelcontextprotocol/sdk (v2.8.1+)">
  Since v2.8.1, `@modelcontextprotocol/sdk` is an **optional peer dependency** of `bunqueue`, not a regular dependency. It's only used by the MCP server, so every queue-only user no longer downloads it. A plain `bun add bunqueue` now installs **7 packages instead of 117** and ships **5.5 MB of `node_modules` instead of 93 MB**, a **94% smaller install** that's also about 3.5× faster on a cold install. The trade-off: when you *do* run the MCP server, you install the SDK yourself, once:

  ```bash
  bun add @modelcontextprotocol/sdk
  ```

  `bunx --package=bunqueue bunqueue-mcp` does **not** auto-install optional peer dependencies, so add the SDK explicitly in the project or environment where the server starts. If it's missing, the launcher exits with code 1 and prints:

  ```text
  [bunqueue-mcp] The MCP server requires "@modelcontextprotocol/sdk" (an optional peer dependency).
  Install it with:  bun add @modelcontextprotocol/sdk
  ```
</Aside>

<Aside type="tip">
  That's all. No server to start, no database to configure. In embedded mode the queue runs in-process; set `DATA_PATH` (or `BUNQUEUE_DATA_PATH`) in the server's `env` to persist jobs to a SQLite file, otherwise state is in-memory for the lifetime of the MCP session. Your agent can immediately add jobs, create cron schedules, set rate limits, register HTTP handlers, and monitor everything.
</Aside>

## How It Works

The MCP server runs as a subprocess spawned by your AI client. It communicates via **stdio** using the JSON-RPC protocol defined by the MCP specification. When the agent calls a tool (e.g. `bunqueue_add_job`), the MCP server executes the operation against the queue backend and returns the result.

The server supports two backend modes: **embedded** (direct SQLite access in the same process) and **TCP** (connects to a remote bunqueue server). In embedded mode, everything runs locally with zero configuration. In TCP mode, the MCP server acts as a client that forwards operations to your production bunqueue instance.

<McpArchitecture />

**Embedded mode** is ideal for local development, single-machine deployments, and CLI tools. With a `DATA_PATH` set, the MCP server manages its own SQLite database with WAL mode for concurrent access; without one, the queue is in-memory and state is lost when the MCP process exits.

**TCP mode** connects to a running bunqueue server, allowing your agent to manage production queues shared across multiple workers and services.

<Aside type="note" title="TCP Mode Parity (v2.6.0)">
  All 73 MCP tools are fully functional in TCP mode. This includes `extend_lock`, `change_delay`, `clear_job_logs`, `set_webhook_enabled`, `compact_memory`, and batch lock extension. The `job_heartbeat` tool also supports a custom `duration` parameter to extend lock TTL for a specific period.
</Aside>

  ```typescript
    storage: { dataPath: './data/queue.db' },

      url: 'https://cloud.bunqueue.io',

    },
  });
  ```

## HTTP Handlers

HTTP handlers solve a fundamental problem: an AI agent can schedule jobs and manage queues, but it cannot run a persistent worker process to actually execute those jobs. HTTP handlers bridge this gap.

When the agent calls `bunqueue_register_handler`, the MCP server spawns an **embedded Worker** inside its own process. This Worker continuously pulls jobs from the specified queue and, for each job, makes an HTTP request to the registered endpoint. The HTTP response is saved as the job result. If the HTTP call fails (non-2xx status or timeout), the job is marked as failed and follows the standard retry/DLQ flow.

This means the agent can set up a fully autonomous pipeline, schedule recurring jobs with cron, auto-process them via HTTP, and check results later, without writing any code or deploying any external service.

<HttpHandlerFlow />

The embedded Worker inherits all standard Worker features: heartbeat, stall detection, retry with backoff, and dead letter queue. It processes jobs sequentially (concurrency 1) to avoid overwhelming the target endpoint.

### Handler configuration

| Parameter | Required | Description |
|-----------|----------|-------------|
| `queue` | Yes | Queue name to attach the handler to |
| `url` | Yes | HTTP endpoint URL to call for each job |
| `method` | Yes | `GET`, `POST`, `PUT`, or `DELETE` |
| `headers` | No | Custom HTTP headers (e.g. `Authorization`, `X-Api-Key`) |
| `body` | No | Fixed request body template for POST/PUT. If omitted, the job's data payload is sent |
| `timeoutMs` | No | Request timeout in milliseconds (default: 30000, range: 1000-120000) |

For `POST` and `PUT` requests, the Worker sends the job's data as JSON body by default. If a `body` template is provided, it overrides the job data. `GET` and `DELETE` requests do not send a body.

### Example: Weather monitoring every 10 seconds

```bash
$ claude

> Register a handler on "meteo" that calls the OpenWeather API

✓ bunqueue_register_handler
  queue: "meteo"
  method: GET
  url: "https://api.openweathermap.org/data/2.5/weather?q=Milan&appid=xxx"
  Worker started. Jobs in "meteo" will be processed via GET.

> Create a cron that pushes a job every 10 seconds

✓ bunqueue_add_cron
  name: "check-meteo"
  queue: "meteo"
  repeatEvery: 10000

# Every 10s: cron creates a job → Worker pulls it → GET request to API →
# response saved as job result → agent can check with bunqueue_get_job_result
```

<Aside type="tip">
  Handlers persist as long as the MCP server process is running. If the agent session ends, the MCP server shuts down and all handlers are stopped. Re-register them in the next session if needed.
</Aside>

## Processing Jobs

Jobs sit in queues until something processes them. Two approaches:

### Option A: HTTP Handlers (no code, agent-managed)

The agent registers an HTTP endpoint on a queue via `bunqueue_register_handler`. The MCP server spawns an embedded Worker that automatically pulls jobs and makes HTTP requests to that endpoint. The response is saved as the job result.

No external process, no deployment, no code. The agent controls the entire lifecycle: register, schedule with cron, monitor results, unregister.

<HttpHandlerLifecycle />

**When to use:** API polling, webhook forwarding, external service calls, health checks, monitoring endpoints. Any use case where the processing logic is just an HTTP call.

```bash
# Agent conversation example
> Register a POST handler on "webhooks" that calls https://api.example.com/ingest

✓ Worker started. Every job in "webhooks" will be sent via POST.

> Add a cron to push a job every 30 seconds

✓ Cron "webhook-trigger" created. Jobs auto-processed via HTTP.
```

### Option B: External Worker (custom logic)

For processing that requires custom code (database writes, file processing, business logic), deploy a separate Worker process. The agent orchestrates (add jobs, schedule crons, monitor progress), the Worker executes.

```typescript
import { Worker } from 'bunqueue/client';

new Worker('emails', async (job) => {
  const { to, subject, body } = job.data;

  await job.updateProgress(25, 'Validating recipient...');
  await validateEmail(to);

  await job.updateProgress(50, 'Sending email...');
  await sendEmail(to, subject, body);

  await job.log(`Email sent to ${to}`);
  return { sent: true, timestamp: Date.now() };
}, { embedded: true });
```

```bash
bun run worker.ts
```

**When to use:** Email sending, image processing, database operations, ML inference, complex business logic, anything that needs code execution beyond a simple HTTP call.

### Comparison

|                    | HTTP Handlers                     | External Worker                  |
| ------------------ | --------------------------------- | -------------------------------- |
| **Setup**          | Zero, agent registers via MCP    | Deploy a Worker process          |
| **Processing**     | HTTP request to an endpoint       | Custom TypeScript function       |
| **Managed by**     | AI agent (register/unregister)    | Developer (deploy/maintain)      |
| **Use case**       | API calls, webhooks, monitoring   | Business logic, DB writes, files |
| **Code required**  | None                              | Yes (Worker definition)          |

## Error Handling

All 73 tools return structured error responses with `isError: true`:

```json
{
  "error": "Human-readable error message"
}
```

Not-found responses for `get_job`, `get_job_by_custom_id`, `get_progress`, and `get_cron` also return `isError: true`. No stack traces or internal details are ever exposed.

## Troubleshooting

### MCP server not connecting

```bash
# Verify bunqueue is installed (bunqueue-mcp is a binary bundled with it)
bun pm ls | grep bunqueue || bun add -g bunqueue

# Check Bun is in PATH
which bun

# Test manually
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"test","version":"1.0"}}}' | bunx bunqueue-mcp
```

### Jobs stuck in waiting

No worker is processing the queue. Either register an HTTP handler or deploy a Worker:

```bash
# Option A: HTTP handler (via agent)
# Ask your agent: "Register a handler on <queue> that calls <url>"

# Option B: External worker
bun run worker.ts
```

### Claude not seeing tools

1. Restart Claude Desktop or Claude Code
2. Check config file syntax (valid JSON)
3. Verify `bunqueue` is installed so the `bunqueue-mcp` binary resolves (`bun add -g bunqueue`)
4. Install the optional MCP SDK peer dependency: `bun add @modelcontextprotocol/sdk` (since v2.8.1 it's not bundled; a missing-SDK launch exits with `[bunqueue-mcp] The MCP server requires "@modelcontextprotocol/sdk"`)
5. Run `bunx bunqueue-mcp` manually to check for errors (a `404` for `bunqueue-mcp` means `bunqueue` isn't installed yet)
