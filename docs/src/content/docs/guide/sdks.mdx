import { Tabs, TabItem } from '@astrojs/starlight/components';

bunqueue ships official client SDKs that implement the native TCP protocol
(msgpack, pipelined) with full feature parity with the built in Bun client.
The server owns every queue semantic, retries with backoff, priorities,
scheduling, stall detection, and the dead letter queue. Client applications
only add jobs and process them, from whatever language they are written in,
against the same queue: one queue, any language.

## Supported platforms

| Platform | Package | Distribution |
|---|---|---|
| Node.js 20 or later, Bun, Deno 2 or later, Cloudflare Workers | `bunqueue-client` | [npm](https://www.npmjs.com/package/bunqueue-client) · [source](https://github.com/egeominotti/bunqueue/tree/main/sdk/typescript) |
| Python 3.9 or later | `bunqueue-client` | PyPI upcoming, [installable from the repository](https://github.com/egeominotti/bunqueue/tree/main/sdk/python) today |
| Bun, embedded in process, no server | `bunqueue` | [Quick Start](/guide/quickstart/) |

Every claim on this page is verified against a real bunqueue server on every
supported platform: 81 end to end scenarios each on Node.js, Deno and Bun,
16 inside workerd, the actual Cloudflare Workers runtime, and 57 in Python.
Every public method of the SDKs is covered by at least one test.

## Getting started

### 1. Run the server

The server is the only component that requires [Bun](https://bun.sh).

```bash
bunx bunqueue start
# or, with Docker and persistent data:
# docker run -d -p 6789:6789 -p 6790:6790 -v bunqueue-data:/app/data ghcr.io/egeominotti/bunqueue:latest
```

Port 6789 serves the TCP protocol used by the SDKs, port 6790 serves the
HTTP API with `/health` and `/metrics`. Additional deployment options are
covered in [Running the Server](/guide/server/).

Run either file with the runtime you already use:

```bash
node --experimental-strip-types app.ts    # Node 22 or later
bun app.ts                                # Bun
deno run -A app.ts                        # Deno 2 or later
python app.py                             # Python
```

The producer and the worker are typically separate services, often in
different languages: a Next.js API adds jobs, a Python service processes
them, against the same queue and the same protocol. Defaults are
`host: 'localhost'` and `port: 6789`, so constructors need no options on a
local setup.

## Core capabilities

Failures retry automatically, three attempts by default. Jobs that exhaust
their retries land in the [dead letter queue](/guide/dlq/), nothing is lost.

```typescript
// Priority, delay, custom retry policy
await queue.add('report', data, { priority: 10, delay: 5000, attempts: 5 });

// Scheduling: run every morning at 09:00
await queue.addCron('daily-report', '0 9 * * *', { type: 'report' });

// Terminal failures: skip retries, straight to the DLQ
throw new UnrecoverableError('malformed payload');

// Pipelines: extract, then transform, then load
await flow.addChain([
  { name: 'extract', queueName: 'etl' },
  { name: 'transform', queueName: 'etl' },
  { name: 'load', queueName: 'etl' },
]);

// Operations: counts, DLQ management, connected workers, statistics
await queue.getJobCounts();
await queue.retryDlq();
await queue.getWorkers();
```

The full surface is available in every SDK with identical semantics: queries
with per state helpers, job control (promote, discard, move, update, change
priority or delay), DLQ management and configuration, schedulers, rate
limiting, global concurrency, stall configuration, webhooks, and metrics.
Python exposes the same methods with snake_case names (`add_cron`,
`add_chain`, `get_job_counts`).

## Simple Mode

`Bunqueue` bundles a Queue and a Worker in a single object, a 1:1 port of
the official client's [Simple Mode](/guide/simple-mode/): routes, onion
middleware, in process retry strategies, a circuit breaker, batch
accumulation, event triggers, job TTL, priority aging, cooperative
cancellation, and deduplication or debounce defaults.

<Tabs>
<TabItem label="Node / Deno / Bun">

```typescript
import { Bunqueue } from 'bunqueue-client';

const app = new Bunqueue('notifications', {
  routes: {
    'send-email': async (job) => ({ sent: true }),
    'send-sms': async (job) => ({ sent: true }),
  },
  concurrency: 10,
  retry: { maxAttempts: 5, strategy: 'jitter' },
  circuitBreaker: { threshold: 5, resetTimeout: 30_000 },
});

app.use(async (job, next) => {
  console.time(job.name);
  const result = await next();
  console.timeEnd(job.name);
  return result;
});

await app.add('send-email', { to: 'alice@example.com' });
await app.cron('daily-digest', '0 9 * * *', { to: 'all' });
```

</TabItem>
<TabItem label="Python">

```python
from bunqueue import Bunqueue

app = Bunqueue(
    "notifications",
    routes={
        "send-email": lambda job: {"sent": True},
        "send-sms": lambda job: {"sent": True},
    },
    concurrency=10,
    retry={"max_attempts": 5, "strategy": "jitter"},
    circuit_breaker={"threshold": 5, "reset_timeout": 30000},
)

def timing(job, next_fn):
    result = next_fn()
    print(f"{job.name} done")
    return result

app.use(timing)

app.add("send-email", {"to": "alice@example.com"})
app.cron("daily-digest", "0 9 * * *", {"to": "all"})
```

</TabItem>
</Tabs>

The only difference from the Bun original: `embedded: true` is not
available, it requires the in process Bun runtime. Connect to a server
instead; the option raises a clear error.

## Cloudflare Workers

The same client runs inside Workers. Enable Node.js compatibility and add
jobs directly from your fetch handlers:

```toml
# wrangler.toml
compatibility_flags = ["nodejs_compat"]
compatibility_date = "2025-01-01"
```

```typescript
import { Queue } from 'bunqueue-client';

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const queue = new Queue('signups', { host: env.BQ_HOST, port: 6789, token: env.BQ_TOKEN, tls: true });
    const job = await queue.add('welcome', await req.json());
    queue.close();
    return Response.json({ queued: job.id });
  },
};
```

Workers are request scoped, so there is no long lived worker loop: produce
from fetch handlers, consume in batches from a
[Cron Trigger](https://developers.cloudflare.com/workers/configuration/cron-triggers/),
pull, process, acknowledge, return. Both patterns are covered by the SDK's
16 scenario suite that runs inside workerd, including Simple Mode. Two
requirements: the server must be reachable from the internet, and TLS
requires a publicly trusted certificate.

## Security

Authentication uses server side tokens, transport security uses native TLS.

```typescript
const queue = new Queue('emails', {
  host: 'queue.example.com',
  port: 6789,
  token: process.env.BUNQUEUE_TOKEN,   // server started with AUTH_TOKENS=...
  tls: true,                            // or { caFile: './ca.pem' } for a custom CA
});
```

Start the server with `AUTH_TOKENS` to require authentication and with
`TLS_CERT_FILE` and `TLS_KEY_FILE` for encrypted transport. The SDKs support
system certificate authorities, a custom CA bundle, and disabled
verification for development environments. Full hardening guidance lives in
the [deployment guide](/guide/deployment/).

## Quality assurance

Every SDK release is validated against a real bunqueue server, spawned
fresh for each run, on every supported runtime:

| Runtime | Verification |
|---|---|
| Node.js | 81 e2e scenarios and 8 integration tests |
| Bun | 81 e2e scenarios and 8 integration tests |
| Deno | 81 e2e scenarios and 8 integration tests, identical test files |
| Cloudflare Workers | 16 scenarios executed inside workerd, full API surface and Simple Mode |
| Python | 57 e2e scenarios and 8 integration tests |

Coverage includes payload limits, unicode integrity, pipelining under
concurrency, server crash and restart with automatic reconnection, lock
survival for jobs longer than the lock TTL, and a realistic multi queue
production scenario with zero loss accounting. Browsers are not supported,
raw TCP sockets are unavailable there: route through your own API instead.
