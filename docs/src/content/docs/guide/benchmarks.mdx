bunqueue supports two deployment modes: **Embedded** (direct SQLite) and **TCP** (network + SQLite). This page shows real benchmark results comparing both modes at scale.

<Aside type="tip">
The only honest benchmark is one you run on your own hardware. Clone the repo and run `bun run bench/comprehensive.ts` to verify these results. The numbers below were re-measured on an Apple M1 Max (Bun 1.3.14) and supersede older figures.
</Aside>

## Install Footprint

Throughput isn't the only number that shrank. As of 2.8.2, a clean `bun add bunqueue` is a featherweight install:

| Metric | bunqueue 2.8.2 | Before (2.7.x) | Change |
|--------|----------------|----------------|--------|
| `node_modules` size | 5.4 MB | 93 MB | **−94%** |
| packages installed | 7 | 117 | **117 → 7** |
| cold install time | ~1.2 s | ~6 s | **up to ~5× faster** |

bunqueue ships just **2 runtime dependencies** — `croner` (cron parsing) and `msgpackr` (binary serialization). SQLite, S3, HTTP, and WebSocket are all built into Bun, so there's nothing else to download. The MCP server's `@modelcontextprotocol/sdk` is an **optional peer dependency**: queue and worker users never pull it in, and you install it once only if you run `bunqueue-mcp`.

<Aside>
The 2.8.0/2.8.1 MCP refactor removed the SDK, `zod`, and the HTTP stack from the install path; 2.8.2 dropped 2.8 MB of unusable sourcemaps from the published package. A new user goes from ~6s to ~1.2s on a cold install.
</Aside>

<Aside>
TCP push scales to **90K ops/sec** at 50K jobs and bulk push peaks around **91K ops/sec**, amortized with connection pooling (32 connections).
</Aside>

<Aside type="caution">
**Read the Process column carefully.** It measures a *single* worker process at `concurrency: 10` draining the queue over the network. Each job's lock lease is bounded by the worker's free concurrency slots (the over‑pull guard), so in steady state the worker issues roughly one pull round‑trip per freed slot — the per‑job network latency, not server throughput, is the bottleneck. Throughput therefore scales with worker concurrency and the number of worker processes, **not** with queue depth:

| Worker concurrency | TCP process (ops/sec) |
|--------------------|-----------------------|
| 10 (default in the bench) | ~182 |
| 50 | ~5,100 |
| 100 | ~4,700 |

Real distributed deployments run many workers and/or higher concurrency, so per‑node processing throughput is in the thousands of ops/sec; for maximum single‑process throughput use **embedded mode** (no network round‑trip per pull). Earlier versions of this page reported much higher single‑worker TCP process numbers that predate the lease‑bounding correctness fix and no longer reproduce.
</Aside>

Raise TCP worker concurrency (or add workers) to close most of that gap; use embedded mode when your workers run in the same process as the queue.
</Aside>

## Benchmark Methodology

The benchmark tests three operations at four different scales (1K, 5K, 10K, 50K jobs):

### 1. Push Test
Sequential push of individual jobs to measure single-job insertion speed.

```typescript
for (let i = 0; i < scale; i++) {
  await queue.add('job', PAYLOAD);
}
```

### 2. Bulk Push Test
Push jobs in batches of 100 to measure bulk insertion efficiency.

```typescript
const jobs = Array.from({ length: 100 }, (_, i) => ({
  name: 'bulk-job',
  data: { ...PAYLOAD, i },
}));

for (let i = 0; i < scale / 100; i++) {
  await queue.addBulk(jobs);
}
```

### 3. Process Test
Push jobs in parallel batches of 500, then process them with 10 concurrent workers.

```typescript
// Push in parallel batches
for (let i = 0; i < scale; i += 500) {
  const promises = [];
  for (let j = 0; j < Math.min(500, scale - i); j++) {
    promises.push(queue.add('job', PAYLOAD));
  }
  await Promise.all(promises);
}

// Wait for all to complete
while (processed < scale) {
  await sleep(5);
}
```

## Why bunqueue is Fast

<CardGrid>
  <Card title="SQLite WAL Mode" icon="seti:db">
    Concurrent reads/writes with memory-mapped I/O via Bun's native FFI bindings.
  </Card>
  <Card title="Auto Sharding" icon="puzzle">
    Auto-detected from CPU cores (power of 2, max 64). Minimizes lock contention.
  </Card>
  <Card title="TCP Pipelining" icon="rocket">
    Multiple commands in flight per connection with reqId-based response matching.
  </Card>
  <Card title="Efficient Structures" icon="seti:config">
    4-ary MinHeap for O(log4 n) priority queues. Skip lists for temporal indexing. LRU caches.
  </Card>
</CardGrid>

## Dependency Chain Latency

Jobs with dependencies (`dependsOn`, `FlowProducer`, parent-child workflows) benefit from event-driven dependency resolution via microtask coalescing, replacing the previous 100ms polling interval.

### Before (polling 100ms via setInterval)

| Scenario | Avg | P50 | P95 | P99 |
|----------|-----|-----|-----|-----|
| **Single dep (A&rarr;B)** | 100.09ms | 100.05ms | 101.91ms | 103.90ms |
| **Chain dep (4 levels)** | 300.83ms | 300.43ms | 304.19ms | 306.72ms |
| **Fan-out (1&rarr;5)** | 100.21ms | 100.11ms | 101.88ms | 105.37ms |

### After (event-driven via microtask)

| Scenario | Avg | P50 | P95 | P99 |
|----------|-----|-----|-----|-----|
| **Single dep (A&rarr;B)** | 23.3&micro;s | 13.8&micro;s | 45.7&micro;s | 100.3&micro;s |
| **Chain dep (4 levels)** | 31.6&micro;s | 30.0&micro;s | 44.6&micro;s | 52.7&micro;s |
| **Fan-out (1&rarr;5)** | 35.0&micro;s | 28.4&micro;s | 43.3&micro;s | 71.9&micro;s |

### Improvement

| Scenario | Before P50 | After P50 | Speedup |
|----------|-----------|----------|---------|
| **Single dep (A&rarr;B)** | 100.05ms | 0.014ms | **~7,200x** |
| **Chain (4 levels)** | 300.43ms | 0.030ms | **~10,000x** |
| **Fan-out (1&rarr;5)** | 100.11ms | 0.028ms | **~3,500x** |

<Aside type="tip">
Dependency chain latency dropped from **hundreds of milliseconds** to **microseconds**. This means multi-step pipelines (ETL, workflows, map-reduce) resolve nearly instantly instead of waiting for polling intervals.
</Aside>
